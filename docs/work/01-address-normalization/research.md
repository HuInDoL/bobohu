# 01. 주소 정리: 코드 리서치

> 단계: 1/4 코드 리서치 · 작성일: 2026-09-26
> 다음 단계: 구현 계획 (`plan.md`). 사용자가 시작하라고 할 때 진행한다.

## 1. 작업 목표
보건복지부 CSV의 주소 826개를 정리해서 다음 두 가지에 쓸 수 있게 만든다.
1. **네이버 Geocoding의 입력값**으로 써서 좌표를 얻는다 (작업 03).
2. `facility` 테이블의 `address`, `sido`, `sigungu` 컬럼을 채운다 (작업 02 CSV 가져오기에서 호출).

이 작업은 **주소 문자열을 정리하는 로직만** 다룬다. CSV를 읽거나 DB에 저장하는 일은 작업 02에서 한다.

## 4. 외부 자료 조사

### 4.1 네이버 Geocoding API (확인함)
- **요청**: `GET https://maps.apigw.ntruss.com/map-geocode/v2/geocode?query={주소}`
- **인증 헤더**: `x-ncp-apigw-api-key-id`(Client ID), `x-ncp-apigw-api-key`(Client Secret)
- **응답의 주요 필드**
  - `roadAddress`, `jibunAddress`: 표준화된 도로명주소와 지번주소
  - `addressElements`: `SIDO`, `SIGUGUN`, `DONGMYUN`, `RI`, `ROAD_NAME`, `BUILDING_NUMBER`, `BUILDING_NAME`, `POSTAL_CODE` 등으로 나뉜 주소 구성요소
  - `x`(경도), `y`(위도)
- 상세주소(동·호·층)를 어떻게 처리하는지는 공식 문서에 설명이 없다 (**확인 필요**, 작업 03에서 실제 호출로 확인).

### 4.2 행정안전부 도로명주소 검색 API (대안)
- `business.juso.go.kr`에서 승인키(`confmKey`)를 받아 쓰는 공공 API다. 응답에 시·도(`siNm`), 시·군·구(`sggNm`), 도로명주소(`roadAddrPart1`) 등이 나뉘어 온다.
- 주소 표준화 자체는 가장 정확하지만 **좌표는 주지 않는다**(**확인 필요**). 승인 절차, 이용 조건, 호출 한도는 이번에 확인하지 못했다 (**확인 필요**).

### 4.3 행정구역 변경 (확인함)
- 2023-06-11 강원도 → 강원특별자치도
- 2023-07-01 경상북도 군위군 → 대구광역시 군위군
- 2024-01-18 전라북도 → 전북특별자치도

### 4.4 CSV 파일 대신 공공데이터포털 Open API를 쓸지 (쓰지 않음)
사용자 질문(2026-09-26): CSV를 Open API로 연결하지 않아도 되는가?
- 공공데이터포털은 일부 파일 데이터를 Open API로 자동 변환해서 제공한다. 이때 API가 주는 내용은 **파일과 같은 표**이므로 항목이나 최신성이 나아지지 않는다.
- 이 데이터는 연 단위 현황 자료다. API로 받으면 키 관리, 장애 처리, 호출 한도만 늘어난다.
- `facility`의 `UNIQUE (source, source_ref)` 덕분에 새 연도 파일이 나오면 같은 가져오기 기능을 다시 실행하면 된다.
- **결론**: 파일로 가져온다. 데이터가 자주 바뀌거나 API에만 있는 항목이 생기면 다시 검토한다.
- **확인 필요**: 이 데이터의 Open API 제공 여부, 업데이트 주기, 2022년보다 최신 파일이 있는지. 최신 파일이 있으면 작업 01 전에 교체하고 3장 분석을 다시 한다.

## 5. 설계에 영향을 주는 발견

### 5.1 표준 주소는 Geocoding 응답에서 얻을 수 있다
Geocoding 응답의 `roadAddress`와 `addressElements`(SIDO, SIGUGUN)는 이미 표준화된 값이다. 그래서 두 가지 방향이 가능하다.
- **A. 직접 규칙으로 완벽하게 정리**: 위 3장의 모든 문제를 코드 규칙으로 해결한다. 외부 API 없이도 `sido`, `sigungu`가 채워진다. 대신 규칙이 많고 예외가 계속 나온다.
- **B. Geocoding이 성공할 만큼만 정리**: 명백한 오류(공백, 중복, 붙은 번호, 상세주소 분리)만 규칙으로 고치고, 표준 주소와 `sido`, `sigungu`는 Geocoding 응답으로 확정한다. 규칙이 적지만, Geocoding 전까지는 `sido`, `sigungu`가 비어 있거나 임시값이다.

### 5.2 상세주소를 분리해야 한다
- 동·호·층, 괄호 참고항목, 건물명 꼬리를 Geocoding 입력에 그대로 넣으면 검색 실패의 원인이 될 수 있다 (**추측**, 작업 03에서 확인).
- 분리한 상세주소를 **저장할지**, 저장한다면 **어디에**(새 컬럼 `address_detail`) 둘지 정해야 한다.

### 5.3 아동 안전: 그룹홈 주소의 호수
- 호수까지 포함된 주소 중 **그룹홈이나 가정형 시설로 보이는 곳이 156건**이다. 대부분 일반 아파트나 빌라의 한 세대다.
- 이 주소를 지도 앱에서 호수까지 공개하면 **아이들이 사는 집의 정확한 위치**가 드러난다. 공공데이터에 있는 정보라도, 앱에서 찾기 쉽게 보여주면 노출 위험이 커진다.
- **법적으로 개인정보는 아니다.** 시설 주소는 개인이 아닌 기관의 정보이고, 정부가 공개한 공공정보다(2026-09-26 사용자 질문으로 표현을 바로잡음). 문제는 법이 아니라 노출 방식이다. CSV는 일부러 찾아서 뒤져야 하지만, 지도 앱은 검색, 마커, 길찾기로 바로 찾아갈 수 있게 만든다. 시설에는 학대로 부모와 분리된 아동도 있을 수 있다.
- 원본 CSV는 이미 `docs/raw/`와 GitHub에 있으므로, DB의 `address_raw`에서만 호수를 지우는 것은 효과가 작다. 원본은 내부에 보존하고 API로 내보내지 않는 방향을 추천한다. [아키텍처의 보안 원칙](../../wiki/architecture.md#6-보안-아키텍처)과 [아동 개인정보 원칙](../../wiki/features/facility-management.md#개인정보-원칙)에 비추어 볼 문제다.
- 주소 정리 단계에서 상세주소를 분리해 두면, 나중에 **공개 범위를 유형별로 다르게** 할 수 있다(예: 그룹홈은 상세주소 비공개, 지도 마커는 대략적인 위치만).

### 5.4 정리 규칙은 계속 바뀐다
원본(`address_raw`)을 보존하고 있으므로, 규칙을 고친 뒤 다시 처리할 수 있다. 정리 로직은 **입력 문자열만 받아 결과를 돌려주는 순수 함수**로 만들면 DB 없이 빠르게 테스트할 수 있다.

### 5.5 검토한 대안: 네이버에서 보육원 데이터를 직접 가져오기 (채택 안 함)
사용자 질문(2026-09-26): 공공데이터 대신 네이버 지도에서 보육원 데이터만 가져올 수는 없는가?
- **NCP Maps에는 장소(POI) 검색이 없다.** 지도 표시, Geocoding, Reverse Geocoding, 길찾기 등만 제공한다.
- **네이버 검색 API(지역 검색)는 한 번에 최대 5건, 다음 페이지 없음(start 최대 1), 하루 25,000회**로 제한된다. 전국 목록 수집에 쓸 수 없다.
- 네이버 지도 웹 화면 크롤링은 이용약관 위반과 법적 위험이 있어 제외한다.
- 데이터 성격도 다르다. 공공데이터는 **정식 신고 시설 목록**이고, 지도 장소 정보는 업체나 사용자가 등록한 것이라 누락이나 어린이집 혼입이 생길 수 있다. 후원 서비스의 신뢰 기준으로는 공식 목록이 맞다.
- **결론**: 기준 목록은 공공데이터, 좌표와 표준 주소는 네이버 Geocoding, 세부 정보는 시설 담당자가 맡는다.
