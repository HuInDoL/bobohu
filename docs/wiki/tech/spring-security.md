# Spring Security

> Spring 애플리케이션의 인증(누구인가)과 인가(무엇을 할 수 있는가)를 담당하는 프레임워크.

## 개념
요청이 컨트롤러에 도착하기 전에 **필터 체인(Filter Chain)**을 거치게 한다. 필터들이 차례대로 인증 정보를 확인하고, 접근 권한을 검사하고, 흔한 공격을 막는다.

## 핵심 내용
- **인증(Authentication)과 인가(Authorization)**: 인증은 사용자가 누구인지 확인하는 것이고, 인가는 그 사용자가 이 자원에 접근해도 되는지 판단하는 것이다.
- **SecurityFilterChain**: 어떤 경로에 어떤 규칙을 적용할지 정의하는 설정 Bean이다.
- **SecurityContext**: 인증에 성공한 사용자 정보를 요청 처리 중에 보관한다.
- **기본 동작**: 의존성만 추가하면 모든 경로에 인증이 걸리고, 임시 계정과 로그인 폼이 자동으로 생긴다. 실제 서비스에서는 직접 설정해서 덮어쓴다.
- **CSRF**: 쿠키 기반 인증일 때, 사용자가 모르게 요청을 보내게 만드는 공격이다. 토큰을 `Authorization` 헤더로 보내는 방식의 API는 이 공격에 해당하지 않아서 보통 끈다.

## 이 프로젝트에서 사용한 방법
- **버전**: Spring Boot 4.1이 관리하는 버전
- **설정 파일**: `server/src/main/java/com/bobohu/common/config/SecurityConfig.java`
- **현재 설정 (뼈대)**
  - **기본값은 거부**: `/actuator/health`만 허용하고 나머지는 모두 `denyAll()`이다. API를 하나 만들 때마다 명시적으로 열어야 한다. 실수로 보호되지 않은 API가 생기는 것을 막는다.
  - **STATELESS**: 서버 세션을 만들지 않는다. 앱이 주 클라이언트라서 토큰 방식을 전제로 한다.
  - **CSRF, HTTP Basic, 로그인 폼 비활성화**: REST API 서버라 필요 없다. 인증 방식을 정할 때 CSRF는 다시 검토한다.
- 인증 방식(JWT 또는 세션)과 역할별 권한은 [아키텍처의 보안 설계](../architecture.md#63-인증과-인가)에 따라 추가한다.

## 트레이드오프
| 장점 | 단점 |
|---|---|
| 검증된 보안 기능을 직접 구현하지 않고 쓸 수 있다 | 필터 체인 구조가 복잡해서 배우기 어렵다 |
| Spring과 자연스럽게 통합된다 (`@PreAuthorize` 등) | 기본 동작을 모르고 쓰면 의도치 않게 막히거나 열린다 |
| OAuth2, JWT 등 표준 방식을 지원한다 | 버전마다 설정 방식이 자주 바뀌었다 (`WebSecurityConfigurerAdapter` 제거 등) |

## 대안 기술
| 대안 | 특징 | 선택하지 않은 이유 |
|---|---|---|
| 직접 만든 필터와 인터셉터 | 단순하고 동작이 다 보인다 | 보안 기능을 직접 구현하면 실수할 위험이 크다 |
| API Gateway에서 인증 처리 | 여러 서비스의 인증을 한곳에서 처리 | 서버가 하나인 모놀리스 구조라 필요 없다 |

## 면접에서 나올 만한 질문
- Q. 인증과 인가의 차이는?
- Q. REST API 서버에서 CSRF를 끈 이유는? 언제 켜야 하나요?
  - A. CSRF는 브라우저가 쿠키를 자동으로 보내는 점을 악용하는 공격입니다. 토큰을 `Authorization` 헤더에 직접 넣어 보내는 방식은 브라우저가 자동으로 붙이지 않으니 해당하지 않습니다. 반대로 쿠키나 세션으로 인증한다면 켜야 합니다.
- Q. 왜 `denyAll()`을 기본으로 했나요?
  - A. 허용 목록 방식이 안전하기 때문입니다. 새 API를 만들고 권한 설정을 잊어버려도 막힌 상태로 남습니다. 그래서 실수가 보안 사고로 이어지지 않습니다.
