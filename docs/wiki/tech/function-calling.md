# Function Calling (도구 호출)

> LLM이 답을 직접 만들지 않고, 미리 정의된 함수 중 무엇을 어떤 인자로 호출할지 결정하게 하는 방식. Tool Use라고도 한다.

## 개념
LLM은 DB에 무엇이 있는지 모르고, 모르는 내용도 그럴듯하게 지어낼 수 있다(환각, hallucination). Function Calling은 LLM의 역할을 **자연어를 구조화된 호출로 바꾸는 일**로 제한한다. 실제 데이터 조회는 서버가 검증된 코드로 한다.

## 핵심 내용
1. 서버가 LLM에게 질문과 **사용 가능한 함수 목록**(이름, 설명, 인자의 JSON 스키마)을 함께 보낸다.
2. LLM이 "이 함수를 이 인자로 호출해" 라고 응답한다.
3. 서버가 인자를 **검증**하고 함수를 실행한다.
4. 실행 결과를 LLM에게 다시 보내면, LLM이 결과를 바탕으로 자연어 답변을 만든다.

## 이 프로젝트에서 사용한 방법 (계획)
[AI 보육원 검색](../features/ai-search.md) 1단계에서 쓴다.

```
"가까운 곳 중 아동 30명 이하, 기독교 재단 소속 보육원 보여줘"
   ↓ LLM
searchOrphanages(sort="DISTANCE", maxChildren=30, affiliation="기독교", lat=.., lng=..)
   ↓ 서버: 인자 검증 후 JPA로 조회 (LLM은 SQL을 만들지 않음)
{ answer: "조건에 맞는 보육원 3곳입니다", orphanages: [{id, name, distance, ...}] }
   ↓ 앱
답변과 카드 목록 → 카드를 누르면 id로 상세 화면
```

- 사용자 위치(좌표)는 LLM이 아니라 앱이 서버에 직접 넘긴다.
- 구현 도구: Spring AI (버전은 착수할 때 확정)

## 트레이드오프
| 장점 | 단점 |
|---|---|
| LLM이 DB에 직접 접근하지 않아 안전하다 | 미리 정의한 함수로 표현할 수 있는 질문만 처리한다 |
| 기존 API와 쿼리를 재사용한다 | 함수 설명과 스키마를 잘 써야 LLM이 올바르게 고른다 |
| 결과가 DB의 실제 데이터라 정확하다 | LLM 호출이 추가되어 응답이 느려지고 비용이 든다 |

## 대안 기술
| 대안 | 특징 | 선택하지 않은 이유 |
|---|---|---|
| Text-to-SQL | LLM이 SQL을 직접 작성. 어떤 질문이든 처리할 수 있다 | 틀린 SQL로 그럴듯한 오답을 낼 수 있고, 보안과 DB 부하 위험이 있다. 주로 사내 분석 도구에서 쓴다 |
| 키워드 검색과 필터 UI만 제공 | 단순하고 빠르다 | 자연어로 질문하는 경험을 줄 수 없다 |

## 면접에서 나올 만한 질문
- Q. LLM이 SQL을 직접 만들게 하지 않은 이유는?
  - A. 소비자용 서비스에서는 정확성과 보안이 가장 중요합니다. Text-to-SQL은 잘못된 쿼리로 틀린 답을 그럴듯하게 낼 수 있고, 권한 밖의 데이터를 조회하거나 무거운 쿼리를 실행할 위험이 있습니다. 그래서 LLM은 검색 조건 추출만 맡기고, 조회는 서버가 검증된 코드로 하도록 설계했습니다.
- Q. LLM이 잘못된 인자를 넘기면 어떻게 처리하나요?
