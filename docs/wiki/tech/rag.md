# RAG (Retrieval-Augmented Generation, 검색 증강 생성)

> 질문과 관련된 문서를 먼저 검색해서 LLM에게 건네주고, 그 내용을 바탕으로 답하게 하는 방식.

## 개념
LLM은 학습하지 않은 데이터(예: 우리 DB의 보육원 소개글)를 모른다. RAG는 질문할 때마다 관련 자료를 찾아 프롬프트에 넣어 준다. 그래서 LLM을 다시 학습시키지 않고도 최신 데이터와 우리 서비스만의 데이터로 답할 수 있다.

## 핵심 내용
- **임베딩(Embedding)**: 텍스트를 의미를 담은 숫자 벡터로 바꾼 것이다. 의미가 비슷한 글은 벡터 공간에서 가깝다.
- **처리 흐름**
  1. **색인(Indexing)**: 문서를 적당한 크기로 자르고(chunking), 임베딩으로 바꿔서 벡터 DB에 저장한다.
  2. **검색(Retrieval)**: 질문도 임베딩으로 바꾸고, 가장 가까운 문서 조각을 찾는다.
  3. **생성(Generation)**: 찾은 문서를 프롬프트에 넣고 LLM이 답을 만든다.
- **벡터 인덱스**: 모든 벡터와 거리를 계산하면 느리다. HNSW 같은 근사 최근접 탐색(ANN) 인덱스로 빠르게 찾는다.
- **하이브리드 검색**: 벡터 검색(의미)과 키워드 검색이나 조건 필터를 함께 쓴다. 예: "서울에 있는" 조건은 필터로, "음악 프로그램"은 벡터 검색으로.

## 이 프로젝트에서 사용한 방법 (계획)
[AI 보육원 검색](../features/ai-search.md) 2단계에서 쓴다.
- **대상 데이터**: 보육원 소개글, 운영 프로그램, 필요 물품 공지 같은 자유 텍스트
- **예시 질문**: "음악 프로그램을 운영하는 곳 있어?", "겨울 옷이 필요한 곳 알려줘"
- **벡터 저장소**: [PostgreSQL](postgresql.md) + pgvector
- **구현 도구**: Spring AI의 VectorStore 추상화 (`PgVectorStore`)
- 임베딩 모델, LLM, 청크 크기는 착수할 때 정한다.

## 트레이드오프
| 장점 | 단점 |
|---|---|
| LLM을 다시 학습시키지 않고 우리 데이터로 답할 수 있다 | 검색이 틀리면 답도 틀린다. 검색 품질이 전체 품질을 좌우한다 |
| 답변의 근거 문서를 함께 보여줄 수 있다 | 청크 크기, 임베딩 모델 등 조정할 것이 많다 |
| 데이터가 바뀌면 색인만 다시 하면 된다 | 임베딩 비용과 벡터 저장 공간이 든다 |

## 대안 기술
| 대안 | 특징 | 선택하지 않은 이유 |
|---|---|---|
| 파인튜닝(Fine-tuning) | 모델 자체를 우리 데이터로 추가 학습 | 비용이 크고 데이터가 바뀔 때마다 다시 학습해야 한다. 사실 정보를 넣는 용도로는 RAG가 낫다 |
| 전체 데이터를 프롬프트에 넣기 | 가장 단순하다 | 데이터가 늘면 컨텍스트 한도와 비용 문제가 생긴다 |
| 전문 검색(Full-text search)만 사용 | 빠르고 싸다 | 단어가 정확히 일치해야 한다. "미술"을 검색하면 "그림 그리기 교실"은 못 찾는다 |

## 면접에서 나올 만한 질문
- Q. RAG와 파인튜닝의 차이, 언제 무엇을 쓰나요?
- Q. 청크 크기는 어떻게 정했나요? 너무 크거나 작으면 어떤 문제가 생기나요?
- Q. 벡터 검색 결과가 부정확할 때 어떻게 개선했나요?
