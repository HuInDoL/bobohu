# Flyway

> DB 스키마 변경을 버전이 붙은 SQL 파일로 관리하는 마이그레이션 도구.

## 개념
코드는 git으로 버전을 관리하는데, DB 테이블 구조는 누가 언제 바꿨는지 알기 어렵다. Flyway는 스키마 변경을 `V1__...sql`, `V2__...sql` 같은 파일로 남기고 순서대로 적용한다. 그래서 어떤 환경이든 같은 스키마를 재현할 수 있다.

## 핵심 내용
- **파일 이름 규칙**: `V{버전}__{설명}.sql` (밑줄 2개). 예: `V1__create_facility.sql`
- **flyway_schema_history 테이블**: 어떤 마이그레이션이 적용됐는지 DB에 기록한다. 앱이 시작할 때 아직 적용되지 않은 파일만 실행한다.
- **체크섬(checksum)**: 이미 적용한 파일을 고치면 체크섬이 달라져서 실행이 실패한다. **적용한 파일은 수정하지 않고 새 파일을 추가**해야 한다.

## 이 프로젝트에서 사용한 방법
- **버전**: Spring Boot 4.1이 관리하는 버전
- **위치**: `server/src/main/resources/db/migration/`
- **적용된 마이그레이션**
  - `V1__create_facility.sql`: 시설 테이블. 설계는 [데이터 모델](../data-model.md) 참고
- **JPA와의 역할 분담**: 스키마는 Flyway로만 바꾼다. JPA는 `ddl-auto: validate`로 엔티티와 스키마가 맞는지 **검증만** 한다.
- **왜**: `ddl-auto: update`는 JPA가 테이블을 알아서 바꿔 준다. 편하지만 컬럼을 지우거나 이름을 바꾸는 변경은 제대로 처리하지 못한다. 운영 DB에 무슨 변경이 적용됐는지 기록도 남지 않는다.

## 트레이드오프
| 장점 | 단점 |
|---|---|
| 스키마 변경 이력이 git에 남는다 | SQL을 직접 써야 한다 |
| 모든 환경(로컬, 테스트, 운영)의 스키마가 같아진다 | 적용된 파일을 고칠 수 없어서, 실수하면 되돌리는 마이그레이션을 새로 써야 한다 |
| 운영 배포 시 스키마 변경이 자동으로 적용된다 | 롤백(되돌리기) 기능은 유료 버전에만 있다 |

## 대안 기술
| 대안 | 특징 | 선택하지 않은 이유 |
|---|---|---|
| Liquibase | XML, YAML, SQL 등으로 변경을 기술. DB 종류에 독립적 | 이 프로젝트는 PostgreSQL 하나만 쓰므로 순수 SQL인 Flyway가 더 단순하다 |
| JPA `ddl-auto: update` | 설정 한 줄로 끝남 | 위 "왜" 참고. 운영에서 쓰면 위험하다 |

## 면접에서 나올 만한 질문
- Q. `ddl-auto: update`를 운영에서 쓰면 안 되는 이유는?
- Q. 이미 적용된 마이그레이션에 실수가 있으면 어떻게 하나요?
  - A. 기존 파일은 수정하지 않고, 바로잡는 내용을 담은 새 마이그레이션 파일을 추가합니다. 기존 파일을 고치면 체크섬이 달라져서 이미 적용된 환경에서 실행이 실패합니다.
